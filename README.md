# ПЗ №8 — подготовка к развёртыванию приложения бронирования оборудования

Копия Django-проекта для выполнения ПЗ №8. Существующие разделы портала, заявок и бронирования оборудования сохранены; основной раздел — `/equipment/`. Исходная папка `срс7 — копия` не изменяется.

## Возможности

- CRUD собственных бронирований через интерфейс и Django REST Framework.
- Процесс: создано → подтверждено → выдано → завершено; отмена созданной/подтверждённой брони.
- Контроль доступности конкретного экземпляра и запрет повторного резервирования занятого ресурса.
- Транзакционное изменение бронирования, экземпляра и журнала. Автоматическая история с инициатором и временем.
- Сессионная авторизация, CSRF и отказ в доступе к чужим объектам, включая историю и бизнес-действия.
- Серверные фильтры по статусу и категории, карточка, редактирование и история без полной перезагрузки.
- Логическое удаление с подтверждением: запись скрывается из API, история остаётся в БД. Активную бронь удалять нельзя.

Это учебная модель самостоятельного учёта: владелец сам отмечает выдачу и возврат. Роль кладовщика и статистика не реализованы. Справочник общий, доступен через API только для чтения; его можно наполнять через Admin или демонстрационную команду.

## Установка и запуск

Команды выполняются из каталога `пз8/`, где находится `manage.py`. Используется Python 3.14; зависимости зафиксированы в `requirements.txt`. В копию намеренно не включены `.venv`, локальная SQLite-база и локальные пароли.

```bash
cd "$HOME/Projects/пз8_споибд/пз8"
python3.14 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_equipment_demo
.venv/bin/python manage.py changepassword student_a
.venv/bin/python manage.py changepassword student_b
.venv/bin/python manage.py runserver
```

Открыть <http://127.0.0.1:8000/>. Раздел оборудования — <http://127.0.0.1:8000/equipment/>. Новая локальная база создаётся миграциями и демонстрационной командой. Команда наполнения создаёт `student_a` и `student_b` без паролей; задайте их отдельно командами `changepassword` выше. Не включайте пароли в исходники и отчёт. Администратор создаётся отдельно при необходимости:

```bash
.venv/bin/python manage.py createsuperuser
```

Для Tabler через CDN требуется интернет. Команда наполнения не сбрасывает базу и не переписывает существующие аккаунты. При полном учебном справочнике повторный вызов ничего не меняет; при конфликте имён или неполном наборе команда отказывает. Для повторения проверки удаления создавайте отдельные записи.

## Демонстрационный набор

Четыре экземпляра двух категорий: `НБ-001`, `НБ-002` (ноутбуки), `ПР-001`, `ПР-002` (проекторы).

`student_a` имеет подтверждённую бронь первого ноутбука, созданные записи второго ноутбука и второго проектора, завершённую и отменённую записи. `student_b` имеет выданный первый проектор и созданную запись на уже зарезервированный первый ноутбук. Последнюю нельзя подтвердить до освобождения ресурса. Все состояния и события формируются через сервисы, а не прямой записью конечных статусов.

Для проверки чужого доступа используйте две отдельные браузерные сессии. Идентификаторы берите из своих записей: числовые id зависят от наполнения БД. В отчёте эти данные следует обозначать как учебные, а не реальные выдачи.

## API

Все маршруты требуют входа. Изменения принимают JSON и CSRF-заголовок `X-CSRFToken` из текущей страницы.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `/api/equipment/` | Общий справочник с доступностью |
| GET, POST | `/api/reservations/` | Собственный список / создание |
| GET, PATCH, DELETE | `/api/reservations/{id}/` | Карточка / редактирование / логическое удаление |
| POST | `/api/reservations/{id}/confirm/` | Зарезервировать свободный экземпляр |
| POST | `/api/reservations/{id}/issue/` | Выдать зарезервированный экземпляр |
| POST | `/api/reservations/{id}/return/` | Принять возврат, освободить экземпляр |
| POST | `/api/reservations/{id}/cancel/` | Отменить созданную или подтверждённую бронь |
| GET | `/api/reservations/{id}/history/` | История собственной неудалённой записи |

POST принимает `{"equipment": 1, "purpose": "Подготовка презентации"}`. PATCH — одно или оба поля только в `new`. Бизнес-действия принимают `{}`. Служебные и неизвестные поля явно отклоняются с 400; PUT выключен (405). Пустой PATCH тоже даёт 400, повторная запись того же значения не создаёт событие.

Списки — массивы без пагинации. Фильтры: `/api/reservations/?status=confirmed&category=Ноутбуки`. Неизвестные значения — 400, валидная пустая выборка — `[]`. На чтение `equipment` — вложенный объект, на запись — id. Для чужих, удалённых и отсутствующих бронирований — 404.

Карточка содержит `id`, `equipment`, `owner`, `purpose`, `status`, `created_at` и `updated_at`. Событие истории содержит `id`, `reservation`, `actor`, `action`, `created_at`, `from_status`, `to_status` и `details`. Ошибки полей возвращаются как `{"purpose": ["Описание ошибки"]}`, бизнес-правил — через `non_field_errors`, доступа — через `detail`.

## Проверки

Базовые тесты не требуют браузера и создают отдельную тестовую БД:

```bash
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py test equipment.tests tickets.tests
node --check equipment/static/equipment/app.js
```

Автоматические браузерные сценарии используют Chromium и временную тестовую БД `test_browser.sqlite3`, не демонстрационную `db.sqlite3`:

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m playwright install chromium
RUN_BROWSER_TESTS=1 .venv/bin/python manage.py test equipment.test_browser
```

В окружении агента Playwright и Chromium уже установлены. При обычном `manage.py test` браузерные сценарии явно пропускаются; это не следует считать их прохождением. Файловая тестовая SQLite используется, чтобы LiveServer и одновременные HTTP-запросы не делили одно in-memory соединение между потоками.

Тест отката подменяет запись события: событие создаётся, затем выбрасывается исключение. Проверяется, что оборудование, бронирование и само событие откатились. Публичного маршрута для генерации сбоя в приложении нет. Браузерные ошибки 500, не-JSON ответы и потеря сети имитируются перехватом ответов только в тестовом браузере.

## Production-подготовка и ограничения

- По умолчанию проект запускается локально с SQLite и `DEBUG=True`. Для production-конфигурации задаются `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=False`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS` и `DATABASE_URL` через окружение; приложение настроено на PostgreSQL, Gunicorn и WhiteNoise.
- Для Render команда сборки: `bash build.sh`; команда запуска: `gunicorn config.wsgi:application --bind 0.0.0.0:$PORT`. Health endpoint: `/healthz/`.
- Не помещайте реальные секреты и строки подключения в Git. Для Render секреты задаются только в настройках Web Service.
- Есть атомарность, условное обновление ресурса и ограничение БД на одну активную бронь. Полноценные конкурентные тесты не выполнялись; гарантии поведения при параллельных записях SQLite не заявляются.
- Интерфейс выполняет загрузки последовательно; на время запроса элементы управления блокируются. Отдельных счётчиков запросов и AbortController нет.
- Production-настройки подготовлены локально, но само приложение ещё не опубликовано на Render. До публикации нужно выполнить шаги из инструкции ПЗ №8 и подтвердить результат реальными проверками.
